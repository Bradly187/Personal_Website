ClinicAgent

An agentic healthcare workflow platform for outpatient clinics utilizing ASP.NET Core, Blazor, and Entity Framework Core over PostgreSQL on a clean, layered architecture. A coordinator LLM routes natural-language requests to specialist sub-agents over real domain services, enforcing business rules and authorization in code. Features include role-based access with TOTP two-factor auth, conflict-aware booking, recurring treatment-plan scheduling, and an automated waitlist. Built initially as a capstone, then hardened into a multi-tenant SaaS. It features FHIR interoperability, HIPAA-style audit logging, structured logging, optimistic concurrency, and 292 automated tests (including real PostgreSQL integration tests via Testcontainers), all codified for AWS with a CI/CD pipeline.

// Scheduling agent

A conversational agent embedded in the sidebar lets staff book appointments, cancel visits, and query the schedule in plain English. Requests are handled by a coordinator LLM that routes to a Google Gemini specialist agent. The agent uses function calling to act only through the application’s existing service layer — so every booking, cancellation, or query it makes respects the same conflict rules, role permissions, and waitlist behavior as the rest of the system. The model never writes to the database directly; it can only invoke the same C#-enforced skills a staff member would.

// Features
Multi-Agent Orchestration Sidebar chat powered by a coordinator LLM that classifies requests and delegates them to one of 6 specialist agents (info, scheduling, waitlist, treatment-plan, intake, triage). The model acts only through the app’s C#-enforced service layer.
MCP Server A Model Context Protocol server (stdio) exposes scheduling tools to any MCP-capable agent such as Claude Desktop. It reuses the same C# domain logic as the web app and REST API, so operating-hours, conflict, and capacity rules hold identically.
Role-Based Access + MFA Six roles: Admin, Clinic Manager, Provider (Therapist), Staff, Patient, and Auditor; each enforced with ASP.NET Core Identity, plus opt-in TOTP two-factor auth.
Conflict-Aware Scheduling Prevents double-booking across therapist, room, and patient — with per-location operating hours, slot durations, and daily capacity, all configurable.
Recurring Treatment Plans One click books a plan’s full series: 2–4 sessions a week at the preferred day and time, falling back to the nearest open slot.
Automated Waitlist Canceled slots are offered to the oldest matching waitlist entry instantly; a background sweep fills the rest and notifies patients.
Request & Approval Workflow Patients request appointments; staff approve or deny; missed visits auto-reschedule to the next open slot.
Multi-Channel Reminders 24-hour appointment reminders in-app, by email, and by SMS; texts are strictly gated on documented patient consent.
Audit & Access Logging Append-only audit trail attributing every change to its user, plus HIPAA-style read-access logging on patient records.
REST API Documented OpenAPI surface with pagination and optimistic concurrency via PostgreSQL xmin row versioning.
Production Observability Serilog structured logging (JSON in production), load-balancer health checks, rate-limited login, and security headers throughout.
// Architecture

Three surfaces drive the clinic — the Blazor UI, the in-app Gemini agent, and the external MCP server — but none of them touch the database directly. Every booking, cancellation, and lookup funnels through the same C#-enforced ISkillExecutor skills and a shared AppointmentSchedulingService, so the no-double-booking, daily-capacity, and business-hours rules hold identically no matter who is asking.

// Cloud architecture

The deployment is defined entirely as code with Terraform. An Application Load Balancer fronts an ECS Fargate service running the containerized app; a managed RDS PostgreSQL instance sits in private subnets, reachable only from the app tier. Database credentials and the seed admin secret are injected at runtime from AWS Secrets Manager, and a GitHub Actions pipeline builds the image to ECR and rolls the service using short-lived, OIDC-federated IAM roles with no long-lived cloud keys.
